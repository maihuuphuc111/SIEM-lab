## Why ClickHouse?

After Kafka buffers Windows Event Logs, the next challenge is selecting a database capable of analyzing large volumes of security events in real time.

In SIEM platforms, two common choices are **ClickHouse** and **Elasticsearch/OpenSearch**. While both can store and query logs, they are optimized for different purposes.

| Feature | ClickHouse | Elasticsearch / OpenSearch | Splunk |
|---------|------------|----------------------------|---------|
| High-speed ingestion | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| Time-series analytics | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| Aggregation (`COUNT`, `GROUP BY`) | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |

| Storage efficiency | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |
| Compression | Excellent | Good | Good |
| Resource usage | Low | High | High |

### Why ClickHouse was chosen

The primary objective of this project is to **detect security incidents as quickly as possible** by analyzing structured Windows Event Logs.

Most SOC dashboards continuously execute time-series queries such as:

- Number of failed logins in the last 5 minutes.
- Top hosts generating security events.
- Event distribution by Event ID.
- Process creation trends over time.
- Authentication activity per user.

These queries rely heavily on filtering, aggregation, and time-range analysis rather than keyword searching.

ClickHouse is specifically optimized for this workload. Its column-oriented storage allows it to read only the required columns, significantly reducing disk I/O and enabling very fast analytical queries over millions or even billions of log records.

On the other hand, **Elasticsearch/OpenSearch** excels at **deep investigation**. When security analysts need to search for specific keywords, commands, scripts, or indicators of compromise (IOCs) within log messages, its inverted index provides much faster full-text search capabilities.

## How ClickHouse Processes Kafka Data

ClickHouse consumes log events from Apache Kafka through a streaming pipeline.

To achieve this, three database objects are used:

```text
                 Apache Kafka
          windows-events-raw-topic
                     │
                     ▼
        ┌──────────────────────────┐
        │ Kafka Engine Table       │
        │ (Consume messages)       │
        └──────────────────────────┘
                     │
                     ▼
        ┌──────────────────────────┐
        │ Materialized View        │
        │ (Parse & Transform)      │
        └──────────────────────────┘
                     │
                     ▼
        ┌──────────────────────────┐
        │ MergeTree Table          │
        │ (Permanent Storage)      │
        └──────────────────────────┘
                     │
                     ▼
                 Grafana
```

### 2. Materialized View

The Materialized View automatically processes each message received from the Kafka Engine table.

<img width="683" height="481" alt="image" src="https://github.com/user-attachments/assets/1528af15-ad4a-4a2e-bb12-ecf9f877d3f8" />


Its responsibilities include:

- Parsing the raw JSON log.
- Extracting required fields.
- Converting data into the appropriate data types.
- Inserting the processed records into the MergeTree table.

This process happens automatically whenever new messages arrive.

---

### 3. MergeTree Table

The MergeTree table is the primary storage table.

Unlike the Kafka Engine table, this table permanently stores all parsed Windows Event Logs and is optimized for analytical queries.

Grafana connects directly to this table to execute SQL queries and visualize security events through dashboards.

Typical queries include:

- Failed login attempts over time.
- Top Event IDs.
- Process creation statistics.
- Authentication activity by host.
- Event trends within a selected time range.
